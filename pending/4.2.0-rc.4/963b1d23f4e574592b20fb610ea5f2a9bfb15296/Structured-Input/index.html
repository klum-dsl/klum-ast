API reference

Pending release evidence. This unlisted snapshot is a protected publication gate, not a public release or alias. Version status.

Structured Input

Structured input applies caller-parsed Maps, Lists and scalars through a Schema's admitted Builder operations. The supported public boundary is generated Factory creation and Builder application; the interpreter is framework internal. Use Create.FromStruct for completed roots, inherited KlumBuilder.applyStruct for an active Builder, and Create.Template.FromStruct for reusable keyless Template bodies.

Parsing remains caller-owned. No JSON/YAML parser, file or URL loading is added. An optional source name is opaque nonempty diagnostic text, never a locator or a model key.

Adopt YAML for a Schema

Use the same Schema for Groovy authoring and a data-only YAML configuration. For a small keyed service, let yamlText contain this document, read by caller code:

service-id: catalog
host: api

The caller chooses a parser dependency and parses the document into a String-keyed Map. For example, using Groovy's YamlSlurper, ordinary Groovy construction and FromStruct produce the same completed Model:

(See: StructuredYamlDocumentaryTest#'caller parsed YAML creates keyed roots and configures an active Builder body'.)

package example

import com.blackbuild.klum.ast.DSL
import com.blackbuild.klum.ast.Key
import com.blackbuild.klum.ast.Struct
import groovy.yaml.YamlSlurper

@DSL class Service {
    @Key @Struct.Name('service-id') String name
    String host
}

def ordinary = Service.Create.With('catalog') {
    host 'api'
}
Map document = new YamlSlurper().parseText(yamlText)
def configured = Service.Create.FromStruct(document, 'service.yaml')
assert configured.name == ordinary.name
assert configured.host == ordinary.host

KlumAST receives the parsed data; it never opens service.yaml. The optional source name is only diagnostic text. A caller that already supplies 'catalog' can instead parse the keyless body host: api and use Service.Create.FromStruct('catalog', body) or apply it to an active Builder.

For editor feedback, apply the Schema Gradle plugin, select the Model binary name (for example, example.Service) in klumSchema.jsonSchema.rootTypes, and run ./gradlew generateKlumJsonSchema. Associate the resulting build/generated/klum-json-schema/example.Service.schema.json with service.yaml in your editor's YAML schema configuration. The JSON Schema recipe explains generation and consumer-owned packaging/association; select a Builder-body artifact instead when caller code supplies root identity. The self-contained artifact requires service-id; the body artifact forbids it.

Keep three boundaries explicit:

  • Parsing: choose and configure the parser, including rejection of duplicate mapping members before they collapse into a Map. A later Struct or JSON Schema check cannot recover lost duplicate keys. The example parser choice alone is not a duplicate-key rejection policy.
  • Execution: preserve Map/List traversal order when it matters. Struct validates and invokes each reached operation in that order, stops at the first failure and retains earlier effects. There is no whole-document payload preflight or rollback; see order and failures.
  • Validation: editor or explicit JSON Schema validation checks the admitted input structure and qualified projected constraints. It does not run automatically in FromStruct or guarantee successful construction. FromStruct runs ordinary Builder lifecycle, materialization and completed-Model validation; defaults, callbacks, converters and model-level rules can still change or reject the result. See validation responsibility.

Relate Groovy and YAML

Struct is a data language for the Schema's admitted construction operations. A YAML mapping member names an input entry; its value supplies that entry's payload. A nested owned body configures a child, while an ordinary typed Map operation receives one Map argument. A sequence populates an admitted collection. These shapes follow the Schema; they are not a serialization of arbitrary Groovy calls.

The examples on this page start after parsing. For each YAML block, supply the equivalent String-keyed Map to the chosen Factory or active Builder. The caller chooses the parser, preserves any required order and rejects duplicate member names before they collapse into a Map. KlumAST neither reads the YAML nor automatically validates JSON Schema.

Representative YAML examples are executable in StructuredYamlDocumentaryTest. They parse YAML with caller-owned YamlSlurper before calling public Struct entry points. The parser is an example choice; KlumAST adds no YAML loader or managed Jackson binding to this path.

What you want to configure Groovy/Struct examples and identity rule
A completed root Factory roots: Create.FromStruct(document); keyed roots either carry their actual key or receive an explicit key with a keyless body.
An existing active Builder Builder application: applyStruct(body) configures the receiver; it never returns a replacement or completes construction.
Direct children and keyed Maps Construction keys: direct keyed children normally carry their own key; keyed Map entries supply identity outside the child body.
Collections Owned child sequences, converter List elements, converter Set elements, converter Map values, CharSequence containers, and derived-key Maps: each has its own declared target and input restrictions.
A domain operation or command The endpoint example, String selection and zero-argument commands: one payload or an empty command mapping, without argument spreading.
A reusable Template Structured Templates: a keyless root recipe; caller code chooses how to apply it.

Ordinary Groovy remains available for forms outside this language. See other relationship boundaries and Groovy forms without a Struct equivalent before assuming parity.

For completion and structural diagnostics while authoring YAML, see the JSON Schema editor-association recipe. The generated schema is editor/validator input: FromStruct / applyStruct do not automatically validate against it. Validation remains editor/consumer-owned; consumers may explicitly validate parsed input before import.

Read a concrete root

A Schema can expose domain operations that configure several properties:

(See: StructuredInputDocumentaryTest#'one structured operation configures several root properties'.)

import com.blackbuild.klum.ast.Builder
import com.blackbuild.klum.ast.DSL

@DSL class Application {
    String host
    int port

    @Builder.Method
    void endpoint(Map<String, String> settings) {
        host = settings.host
        port = Integer.parseInt(settings.port)
    }
}

For that Schema, the parsed configuration is a Map such as:

def ordinary = Application.Create.With {
    endpoint(host: 'api', port: '8080')
}
def parsed = [endpoint: [host: 'api', port: '8080']]
def application = Application.Create.FromStruct(parsed, 'application.yaml')
assert application.host == 'api'
assert application.port == 8080

The corresponding YAML supplies one Map payload to endpoint; port is quoted because the operation declares Map<String, String>, even though its body produces an integer property:

(See: StructuredYamlDocumentaryTest#'caller parsed YAML supplies one nested Map payload to an authored operation'.)

endpoint:
  host: api
  port: "8080"

The admitted endpoint operation sets host to api and port to 8080. Use a Factory selecting a concrete Schema; its ordinary default-implementation selection still applies. Root input must be a Map with String keys. A self-contained keyed document supplies its actual key member; a caller-pre-keyed body omits it. Supplied direct children retain their own positional key rules in either form.

Compile Schemas successfully with the current KlumAST compiler and distribute their generated classes together. Missing or inconsistent generated structured-input metadata reports recompile/package guidance. An in-memory-only Schema without packaged generated metadata cannot use this route.

Factory roots

The common Factory signatures are T FromStruct(Map<?, ?> document) and T FromStruct(Map<?, ?> document, String sourceName). Keyed Factories additionally expose T FromStruct(String rootKey, Map<?, ?> body) and the trailing String sourceName overload. All return completed Models after ordinary lifecycle, materialization and validation.

Java callers use the generated Factory directly (for the Service Schema below):

Service document = Service.Create.FromStruct(Map.of("service-id", "catalog", "host", "api"));
Service explicit = Service.Create.FromStruct("catalog", Map.of("host", "api"), "request");

(See: StructuredFactoryTest#'Factory documents carry their own root identity' and StructuredFactoryTest#'explicit root keys configure one ordinary lifecycle'.)

@DSL class Identity {
    @Key @Struct.Name('service-id') String name
}
@DSL class Service extends Identity { String host }

def document = Service.Create.FromStruct(['service-id': 'catalog', host: 'api'])
def explicit = Service.Create.FromStruct('catalog', [host: 'api'], 'request')
assert document.name == explicit.name

For the self-contained document, YAML includes service-id: catalog alongside host: api. For the explicit-key Factory call, YAML contains only host: api; caller code supplies 'catalog'. The same keyless host body can be applied inside Service.Create.With('catalog') using applyStruct([host: 'api']).

(See: StructuredYamlDocumentaryTest#'caller parsed YAML creates keyed roots and configures an active Builder body'.)

service-id: catalog
host: api

The explicit-key body forbids service-id, even if its value equals the argument. Both root forms run exactly one root PostApply, with identity available before PostCreate. sourceName is optional, opaque diagnostic text only; null and empty explicit labels reject. Ordinary calls generate a label identifying the Factory capability. File-like and URL-like labels are never opened, normalized or used as identity. Factory access initializes its ordinary Create field; the internal contract inspector's no-user-code guarantee is a tooling property, not a promise to suppress normal class initialization when accessing a Factory.

FromStruct does not appear on AsBuilder() or relationship factories. Create.FromMap remains the separate copy/type-hint/conversion/custom-Factory route; managed Jackson retains its independent contract.

Root Builder overlays

Append an ordinary Builder closure to any existing root FromStruct form:

  • FromStruct(document, overlay) or FromStruct(document, sourceName, overlay);
  • keyed FromStruct(rootKey, body, overlay) or FromStruct(rootKey, body, sourceName, overlay).

The generated Factory returns the exact Model type and delegates the closure to its public Builder with DELEGATE_ONLY. The overlay runs after successful Struct execution in the same root configuration, before one root PostApply and the ordinary graph lifecycle, materialization and validation. It can supply completed external LINK values needed by later lifecycle handling.

(See: RootStructOverlayTest#'supplies a completed environment after Struct input before the root lifecycle tail'.)

@DSL class Environment { String name }
@DSL class Application {
    String title
    @Field(FieldType.LINK) Environment environment
}
def selectedEnvironment = Environment.Create.With(name: 'production')
def document = [title: 'orders']
def orders = Application.Create.FromStruct(document, 'orders.yaml') {
    environment selectedEnvironment
}
assert orders.title == 'orders'
assert orders.environment.is(selectedEnvironment)

Templates and root PostCreate precede Struct input and the overlay. Struct operations and immediate child callbacks cannot see overlay-supplied state. Ordinary setters, collection operations, deferred actions and later callbacks retain their usual behavior; the overlay has no permanent priority. External completed LINK targets retain identity and are excluded from owned lifecycle traversal.

Source/type/root-shape/static-contract and construction-key checks retain their existing allocation boundaries. Ordered payload failures retain earlier effects and skip the overlay. The overlay cannot repair a missing construction key or a failed operation. Overlay and lifecycle failures return no completed root and use normal session cleanup. Each invocation clones the overlay before changing its delegate; captured mutable state remains caller-owned. A typed null Closure acts as no overlay.

These overloads belong only to ordinary root Factories. They add no Template, AsBuilder, Builder application, file/URL/text, parser or context-channel variant. Recompile existing Schemas to expose the generated members. FromStruct(document, null) and keyed FromStruct(rootKey, body, null) can become ambiguous between String and Closure; use an explicit type. See migration.

Consumer-owned Environment setup

The caller may construct its Environment from a separate parsed YAML mapping before loading the consuming root. The same ordinary overlay then supplies the completed Environment as a LINK; parsing and Environment selection remain caller responsibilities:

(See: RootRecipeConsumerTest#'JAR-only clients consume recipe and Struct overlays and consumer-owned lifecycle context with named modules=#named'.)

def selectedEnvironment = Environment.Create.FromStruct(environmentDocument, 'environment.yaml')
def orders = Application.Create.FromStruct(applicationDocument, 'orders.yaml') {
    environment selectedEnvironment
    image 'overlay:v2'
}
assert orders.environment.is(selectedEnvironment)

The JAR-only documentary qualification uses an Application with owned Services. Each Service's immediate PostCreate/PostApply runs without that Environment; its AutoLink callback then obtains the root's Environment through its Owner, and Default derives its endpoint and image. Validation checks completed root/child identity and one lifecycle tail. Repeated roots share the exact completed Environment without owning it or revisiting its lifecycle. The fixture starts at already-parsed mappings and does not qualify a YAML parser or a specific adopter.

If a Schema needs dependencies during earlier callbacks, its own factory/setup must provide them before those callbacks run. A root overlay does not change their timing or provide context while Struct operations execute.

Metadata protocol

Structured input and JSON Schema generation require Schemas compiled with a matching supported metadata protocol. Older or incomplete Builder contracts are rejected; recompile the participating Schema artifacts.

The current compiler explicitly emits GeneratedInput.Schema.version=1 on every declaring public Builder. Both consumers require exactly that version and complete naming, exclusion, constraint, projection, source-provenance, key, literal-alternative association/count and inert example-array facts. The optional field-presence member rawInputRequired is true for marked fields; omission and explicit false both mean false. Its absence is not a fallback for other required facts. Malformed/duplicate/contradictory supplied presence facts fail before initialization, input mutation or schema output replacement. Schema.version is the sole protocol version; LiteralAlternative has no separate version member. Recompile participating Schemas with matching compiler/runtime/plugin artifacts; removed or unknown members have no compatibility decoder. The rule also applies to inherited and participating owned contracts across project/JAR boundaries. Missing, older, future, malformed or incomplete metadata fails before input execution; a version marker alone does not establish completeness. There is no identity-only mode, annotation reconstruction or partial legacy support. The admitted ownership closure is checked before execution, including omitted owned inputs; the per-read cache terminates recursive contracts. Excluded targets and unrelated classpath classes are not scanned.

Type naming profiles

Select @Struct.Naming on a Schema type to use the same exact member tokens in structured input and generated JSON Schema. Its required value is Struct.Naming.Profile.IDENTITY or Struct.Naming.Profile.KEBAB_CASE; there is no default value or caller/plugin selector.

(See: InputNamingProfileTest#'choose kebab member names while keeping owned values and data keys independent'.)

import com.blackbuild.klum.ast.DSL
import com.blackbuild.klum.ast.Struct

@DSL class ServiceBase { String displayName }
@Struct.Naming(Struct.Naming.Profile.KEBAB_CASE)
@DSL class Service extends ServiceBase {
    String serviceName
    Map<String, String> labels
    Details serviceDetails
}
@DSL class Details { String nativeName }

def parsed = ['display-name': 'Catalog', 'service-name': 'catalog', labels: ['Team/Blue': 'ops'],
              'service-details': [nativeName: 'own policy']]
// Configures serviceName as 'catalog'; the data key 'Team/Blue' stays literal.

An unannotated child inherits an explicit ancestor profile. Repeating that profile is permitted; a different explicit choice rejects the subtype with both declaring types/artifacts in the diagnostic. An explicit IDENTITY also binds descendants. When every ancestor is unannotated, the first annotated child chooses its complete effective grammar, including inherited members; the standalone ancestor keeps native spelling. Owned values resolve their own type hierarchy, as Details does above. Ownership does not cascade the owner's profile.

KEBAB_CASE inserts a hyphen before ASCII uppercase after ASCII lowercase/digits, and at an uppercase acronym-to-word boundary, then lowercases only ASCII A-Z. It uses original adjacency: URLValue becomes url-value, XML2Parser becomes xml2-parser, and version2URL becomes version2-url. Existing separators and non-ASCII characters remain unchanged: already_snake stays as written and ÅngströmURL becomes Ångström-url. There is no Unicode normalization, transliteration or locale rule. Malformed UTF-16 in transformed native metadata is rejected.

Profiles affect only eligible field, construction-key and admitted authored-operation member names. They add no native-name alias. Data Map keys, keyed-instance keys, fixed identity values, enum value tokens and operation Map-payload keys remain literal. Existing supported nonempty @JsonProperty names remain exact; they are never transformed. Empty @JsonProperty falls back to native/profile spelling. @JsonIgnore/@JsonIgnore(true) excludes before naming, and @JsonIgnore(false) is neutral. Naming does not admit otherwise unsupported declarations. Use literal names and exclusion for Klum-owned overrides without a Jackson dependency.

Under a nonidentity profile, collisions between eligible member tokens reject the type with both source declarations, before input executes. A literal rename can remove the collision. Construction-key collisions still depend on whether the input position supplies the key as a member; outer instance keys and explicit root keys retain authority. No-profile and identity collision behavior is unchanged. Match compiler/runtime/plugin versions and recompile a selected type hierarchy; missing, unknown or malformed required naming facts fail with recompile/package guidance. See migration.

Literal names and exclusion

Use com.blackbuild.klum.ast.Struct.Name and Struct.Ignore on source fields (including construction keys) or already admitted authored @Builder.Method operations. @Struct.Name requires a nonempty exact String; spaces, punctuation and case are preserved. @Struct.Ignore is a marker. Both have runtime retention and FIELD/METHOD targets.

(See: InputLiteralTest#'choose exact external names and exclude internal configuration'.)

import com.blackbuild.klum.ast.*

@Struct.Naming(Struct.Naming.Profile.KEBAB_CASE)
@DSL class Service {
    @Struct.Name('service.id') String serviceName
    @Struct.Ignore String internalNote
    @Builder.Method @Struct.Name('configure/URL')
    void configureEndpoint(String value) { serviceName = value }
    @Builder.Method @Struct.Ignore
    void configureInternally(String value) { internalNote = value }
}

def parsed = ['service.id': 'catalog'] // Configures serviceName as 'catalog'.
// Ordinary Groovy configuration keeps its authored names, including ignored members.
def configured = Service.Create.With { serviceName 'groovy'; configureInternally 'private' }
assert configured.internalNote == 'private'

Eligibility and exclusion come first, then a compatible explicit literal, then the inherited/local type profile, then identity. Naming cannot admit unsupported types or operations. A literal adds no native/profile alias and can separate entries that would collide under a nonidentity profile. Unresolved nonidentity collisions fail with both source declarations; existing identity collision rejection is unchanged.

Supported @JsonProperty/@JsonIgnore bridging remains available. Equal nonempty Struct.Name and JsonProperty names coalesce; different names fail deterministically with both annotation origins, even when excluded. Empty JsonProperty falls back; empty Struct.Name is invalid. Struct.Ignore or true/absent-value JsonIgnore excludes; false JsonIgnore cannot undo exclusion. Exclusion and a compatible rename can coexist.

Both consumers use compiler-folded facts on the exact public Builder declarations. Exclusion removes members from structured input and generated JSON Schema; it changes no ordinary Groovy configuration, runtime validation, defaults or completed Model API. An ignored required construction key still needs an external root key, Schema derivation or keyed-Map identity; it cannot make an otherwise self-contained key position valid. Data/instance keys remain literal. Managed Jackson import remains independently configured: use the Jackson literal too when both routes need one spelling. There is no automatic mapper adapter. Recompile Schemas and align compiler/runtime/plugin versions; see migration.

Raw-input presence

@Struct.Required marks an admitted field for the containing object's generated JSON Schema required array. Direct use and effective domain annotations (including transitive composition) have the same meaning. Inherited fields, explicit names and type naming profiles retain their normal effective identity. It neither admits excluded fields nor marks Builder operations; Struct.Ignore plus the marker is a compile/contract error.

This policy is separate from construction-key identity, completed-Model @Required and Jakarta validation. Ordinary Create.FromStruct([:]), Create.With { } and active Builder applyStruct([:]) still accept omission, subject to the Schema's existing construction and validation behavior. Defaults, initializers, Templates, lifecycle, null admission and ordered failures are unchanged. Only an editor or explicitly invoked external JSON Schema validator reports a missing marked input member. Presence does not test Groovy truth or imply non-nullness, and is independent of constraint projection policy. An owned child requirement does not require its optional parent relationship.

See raw-input field presence for the direct/domain Schema example, resolved names, required-key positions and documentary test plus external Draft 2020-12 oracle. Recompile participating Schemas with matching tools and regenerate schema output as described in Migration.

Construction keys

Self-contained keyed documents require the actual Schema @Key String member. A supplied direct owned keyed child requires its key too, at any depth, unless its relationship supplies identity through @Field.key or a fixed Cluster key. An absent optional child remains absent. Unkeyed roots have no synthetic identity property.

(See: StructuredInputKeyDocumentaryTest#'self-contained documents carry root and direct-child keys while Maps supply outer keys'.)

import com.blackbuild.klum.ast.DSL
import com.blackbuild.klum.ast.Key
import com.fasterxml.jackson.annotation.JsonProperty

@DSL class Deployment {
    @Key String name
    Service service
    Map<String, Service> services
}
@DSL class Service {
    @Key @JsonProperty('service-id') String name
    String image
}

The self-contained parsed document includes root and direct-child identity:

def parsed = [name: 'production',
              service: ['service-id': 'catalog', image: 'catalog:1.0'],
              services: [worker: [image: 'worker:1.0']]]
def deployment = Deployment.Create.FromStruct(parsed)

Root identity is production, direct-child identity is catalog, and the literal Map entry supplies worker.

This Map could come from YAML such as the following. The caller owns parsing; the source name is only diagnostic text.

(See: StructuredYamlDocumentaryTest#'caller parsed YAML supplies direct child identity and literal Map entry identity'.)

name: production
service:
  service-id: catalog
  image: catalog:1.0
services:
  worker:
    image: worker:1.0
Object position Identity authority Actual key member in that object's payload
Self-contained keyed root Input Required String
Caller-pre-keyed root body Explicit rootKey Forbidden, even if equal
Active Builder body Allocated Builder Forbidden, even if equal
Supplied direct keyed child Input, unless Schema supplies identity Required String
Fixed/derived-key direct child, including fixed Cluster fields Schema relationship Forbidden, even if equal
Keyed owned Map value Outer literal Map entry Forbidden, even if equal

Thus services.worker must omit service-id: worker already supplies its identity. A nested direct child inside that body still requires its own key when its relationship has no provider. Key names are resolved on the actual compiler-selected declaration, including binary inherited keys: @Struct.Ignore or @JsonIgnore(true) excludes it, a compatible nonempty literal @Struct.Name or @JsonProperty renames it, then the effective type profile/native name applies. Empty @JsonProperty uses that fallback; @JsonIgnore(false) leaves the declaration admitted under its otherwise resolved name. Renames add no alias. An ordinary unannotated key property remains normal input; an independently admitted operation with an old/native spelling keeps its meaning.

Key values must be exact Strings. Empty Strings are accepted; null, numbers, booleans, GStrings and containers reject without coercion. An ignored key cannot support a self-contained root or an input-key direct child. An external-name collision between that required key and an admitted operation rejects before allocation, naming both declarations. Keyless positions retain their ordinary operation admission. Use an explicit root key, a Schema key provider or a keyed Map where appropriate for an ignored key. A provider is never evaluated to compare an inner key.

A caller-pre-keyed root body leaves out the root key while retaining the supplied direct child's identity:

def body = [service: ['service-id': 'catalog', image: 'catalog:1.0']]

The caller supplies root identity separately through the keyed Factory argument or an already prepared Builder.

Compile and ship matching compiler/runtime/plugin versions with current generated key facts. Missing facts produce recompile/package guidance; the interpreter does not guess key names or derive identity from a filename or URL. Create.FromMap retains its separate copy/type-hint behavior. Schema generation adds no runtime entry point or file/URL loading API.

For editor/validator tooling of caller-pre-keyed bodies, explicitly select the Builder-body schema artifact. Default root schemas continue to describe self-contained input; generation never derives identity from source names.

Apply to an active Builder

The public capability is void applyStruct(Map<?, ?> body[, String sourceName]) on KlumBuilder, inherited by generated Builder contracts. It configures the existing receiver and does not replace or complete it. The interpreter remains internal. See the accepted signature and migration contract.

A caller prepares the Builder through ordinary construction before applying a parsed body. The documentary fixture qualifies the grammar and lifecycle through the public Builder capability: StructuredInputDocumentaryTest#'Holder supplies completed LINK context for later phases after applying an already-prepared Builder'.

Active Builders

Java helpers can preserve their exact Builder type while calling the void capability:

static <B extends KlumBuilder<?>> B configure(B target, Map<?, ?> body, String sourceName) {
    target.applyStruct(body, sourceName);
    return target;
}

(See: StructuredFactoryTest#'active Builders apply structured bodies without completing construction'.)

def service = Service.Create.With('catalog') {
    applyStruct([host: 'first'])
    applyStruct([host: 'api'], 'request')
}
assert service.host == 'api'

Each successful applyStruct adds one PostApply; the enclosing With performs its own PostApply afterward. The common Map signatures are framework capabilities, excluded from structured operations and absent from completed Models. applyStruct(Map) and applyStruct(Map, String) are reserved: a colliding Schema method, field configurator or default-argument overload fails compilation. Rename the conflicting declaration; distinct overloads remain legal.

That fixture uses an owned application field and a completed environment LINK needed only by later phases. AsBuilder().One() has already run PostCreate and PostApply. Dependencies needed by those early callbacks must be provided by an appropriate Schema-specific construction path before they run; assigning a LINK afterward cannot supply an earlier callback. Structured input does not inject context or change lifecycle timing.

The target payload cannot carry its actual construction key; the target already owns identity. Nested direct children continue to follow construction keys.

Application requires an active same-thread Construction session and an unsealed ordinary generated Builder. It adds one PostApply for this application, without replaying PostCreate or completing the Builder. The enclosing construction still performs its own ordinary application/completion work. Completed, stale, wrong-thread and Template Builders reject. Root construction cannot start an independent nested root.

Concrete owned relationships follow the same rules when their generated Builder contracts come from compatible binary API/Schema dependencies. Interpretation needs no Schema sources, IDE source mirrors or Javadocs.

Supported field containers are List, Set, SortedSet, NavigableSet, EnumSet, Map, SortedMap and NavigableMap. Normal Builder mechanics manage the declared container, including set deduplication and sorted storage. Operation arguments and nested ordinary data containers use List/Map; there is no construction of concrete/custom container arguments or broad Collection/Iterable arguments. An ordinary non-DSL scalar field also admits an exact, unambiguous generated String converter route, including field closures, same-compilation values and separately compiled external adapters. This uses an already-generated public Builder projection; it does not add converter discovery or make omitted/colliding projections callable.

A blank YAML value (resetTimeout:) and explicit null are not call markers. Null, nonempty Maps, Lists and scalars reject; resetTimeout! is an unknown name. Parsing stays caller-owned. The command follows the same literal/profile naming, exclusion, exact inherited override and collision rules as other admitted entries; payload shape never chooses an overload. @Struct.Operation retains its String-selection role and is not needed on a command. Query, lifecycle and framework helpers are not commands. Inherited overrides own their names and exclusions, so an old parent spelling cannot call renamed code.

Order and failures apply: a command reached before a later invalid member may execute; no later operation runs after failure. Generated JSON Schema describes a closed empty object. Recompile participating Schema hierarchies with matching compiler/runtime/plugin artifacts for the required command-role facts; see migration.

Order and failures

Input is checked one operation at a time and execution stops at the first encountered invalid name, payload, type, child or invocation. Earlier operations and their ordinary side effects remain; later operations are not reached. There is no whole-document payload preflight or rollback. A failed root construction returns no completed Model. A failed Builder application can leave the caller's Builder partially configured; it does not reset or complete it, and does not run PostApply for the failed application.

Source, root Map, active same-thread unsealed target and complete static contract checks precede traversal. The full admitted ownership contract graph is verified even for omitted children, without executing user code. A newly allocated keyed root or direct child reads its required construction key before allocation and PostCreate, wherever that key occurs in its Map. Its remaining body is not checked ahead. A missing or invalid required key prevents that object's allocation; earlier siblings may already have run. Externally supplied identity remains authoritative and inner keys reject when reached.

A typed List/Map passed as one authored operation argument is validated as one payload before that invocation. Generated population routes instead check and invoke each element or Map entry in supplied order. Cyclic containers reject when reached; repeated acyclic shared values remain allowed. The interpreter does not take a whole-input snapshot.

(See: StructuredInputRuntimeTest#'supplied operation order configures the Builder until the first invalid member'.)

def parsed = [host: 'api', unknown: true, port: 8080]
// host is applied first; unknown then fails; port is not reached.

A caller that catches the failure must explicitly choose whether to abandon construction or retain the partial state. The internal grammar test qualifies this behavior; no public reader or new construction API is introduced here.

Execution follows each supplied Map's iteration order recursively and each List's element order. An insertion-ordered Map preserves the caller's chosen order; an unordered Map exposes its own iteration order. There is no portable parser source-order guarantee or sorting imposed by the interpreter. Reversing order-sensitive operations can change the result. Normal lifecycle, ownership, defaults, AutoLink, LinkTo, materialization and validation remain in their usual phases.

Local input/dispatch failures use KlumModelException, naming the source, escaped JSON Pointer, external name, public Builder contract and expected/actual shape or type. Pointer tokens escape / as ~1 and ~ as ~0; List indices are included. Original operation causes are retained. Late lifecycle/validation failures keep their normal framework behavior and are not attributed to an invented last input leaf. No input provenance is retained on the completed Model. A Template or earlier operation may already have populated a child. Ordinary same-key reuse and different-key rejection still apply during execution. A parser must reject repeated raw JSON/YAML member names before collapsing them into a Map; neither this API nor JSON Schema can recover discarded duplicates.

Jackson integration remains an independent foreign-data binding route with its existing callback and codec behavior. Structured input is opt-in and does not change named-parameter configuration or Jackson.

The internal grammar qualification fixtures live in StructuredInputDocumentaryTest: “one structured operation configures several root properties” and “Holder supplies completed LINK context for later phases after applying an already-prepared Builder”. The key examples live in StructuredInputKeyDocumentaryTest, linked to #954. Related language work: #932; optional matching JSON Schema generation remains #529.

Advisory input examples

@Struct.Examples provides documentary strings. They are emitted as JSON Schema string examples, without parsing or validation against the property type or runtime constraints. See generated JSON Schema.

(See: InputExamplesTest#'document example values without supplying defaults or changing input admission'.)

@DSL class Service {
    @Struct.Examples(['Catalog', 'catalog.internal']) String displayName
}

def configured = [displayName: 'Configured']
def omitted = [:]
// The explicit value configures displayName; omission does not supply an example as a default.

Documentation strings do not supply values or change input admission, naming/exclusion, defaults, validation or lifecycle. The shared byte reader checks required string-array metadata without interpreting its contents. Compiler constant capture never reads a static field reflectively to obtain a value. Owned/inherited public Builder declarations remain the authority; no Model-byte fallback, Javadoc transport, provider or callback participates.

Documentary constraint meta-annotations

@Struct.ConstraintDescription('literal text') belongs on an annotation type. It adds documentary text for Schema fields using that annotation; it supplies no validation, default, example or input-admission rule. Bean composed constraints may host first-level composing constraints for the built-in JSON Schema mappings. These facts do not enforce constraints at Java/Groovy call boundaries or change structured-input interpretation. Projection policies and the exact composition boundary are described in JSON Schema.
