API reference

Pending release evidence. This unlisted snapshot is a protected publication gate, not a public release or alias. Version status.

Migration

Opt-in JSON Schema tooling

The Schema plugin's generateKlumJsonSchema task uses compiled public contracts with current generated input enrichment. Recompile older Schemas and keep plugin/compiler/runtime versions aligned before enabling it. Configure explicit DSL Model names as strings; output filenames use those fully qualified Model names. No source discovery, input parser or publication change is required. See JSON Schema generation.

Unreleased

Raw-input presence and the 4.2 contract

For @Struct.Required, recompile every participating Schema/API, binary parent, derived and owned artifact with matching 4.2 annotations/compiler/runtime/Schema-plugin inputs, then regenerate JSON Schema and distribute it to editors/clients. Rebuilding only the final application does not regenerate its dependencies' Builder metadata. Direct and transitive domain-annotation markers need the same matched compilation path.

Development protocol v1 remains unreleased. Its current contract adds optional field presence: marked fields emit true; omission and explicit false mean false. Earlier development-v1 producers/readers are outside the supported contract; there is no historical compatibility matrix or partial-metadata fallback. All other required facts and participating contracts must be complete. Missing/incompatible versions or malformed facts fail closed; this adds no stale-artifact or release-provenance detector.

This feature changes generated JSON Schema presence only. It does not enforce omission in FromStruct/applyStruct, change null/default/lifecycle behavior or reinterpret @Required/Jakarta validation. See the Schema example and documentary coverage and Struct import guidance.

Before a public 4.2 RC, maintainers must record the final v1 freeze, recompile the entire participating Schema closure, and qualify the exact public candidate with its matching published coordinates and regenerated schemas. Branch-local G3/G4/G5, binary and G4/G5 JPMS evidence does not complete those release obligations. An incompatible post-freeze change requires a new decision and a further RC (#1055).

Reserved Builder copy signature

Schema-authored Builder methods with effective signature copyFrom(Object) are now rejected at compilation: they shadow a framework Builder copy route and can skip its Construction-session and sealed-state checks. This includes untyped parameters, generic parameters erased to Object, inherited methods and overloads produced by default arguments. Rename the conflicting operation and recompile affected Schemas, including the declaring parent when the conflict is inherited. Distinct overloads such as copyFrom(String) remain allowed, and ordinary Map/Model copying keeps its existing behavior.

This is source prevention only (#1011). Upgrading the compiler or runtime does not repair an already compiled conflicting Schema. Runtime hardening for those binaries is separate follow-up work. See Template copying.

Generated compiler provenance (4.2)

Recompile Schema artifacts to record the exact emitting compiler version on each abstract and concrete Schema class. Existing unmarked binaries remain usable; reflection returns no provenance for them. The runtime-retained GeneratedSchema marker is generated automatically and requires no handwritten annotation or Model changes. It adds no runtime compatibility check or minimum-runtime requirement. See Schema Compiler Provenance.

Compiled root recipe overlays

Recompile Schema artifacts with the matched compiler/runtime to expose Create.From(DelegatingScriptClass) { ... }, Create.FromClasspath { ... } and Create.FromClasspath(modelLoader) { ... }. Existing no-overlay binary calls remain supported. Audit custom Factory (Class, Closure), (Closure) and (ClassLoader, Closure) methods for collisions or intentional overrides. An untyped FromClasspath(null) may now be ambiguous between ClassLoader and Closure; type the argument explicitly. Overlay routes accept only DelegatingScript; regular Script producers keep their existing no-overlay operation. See root recipe overlays for timing and supported sources. Keep generated IDE mirrors out of downstream compilation; the compiled Schema JAR supplies the public Factory contract. Groovy 3 remains classpath-only; Groovy 4/5 retain the ordinary named-module boundary. See Factory consumer guidance. Other source overlay forms remain unavailable.

Structured Factory and Builder capabilities

The unreleased development reader KlumStructuredInput has been removed without a forwarding alias. Replace its root calls with Type.Create.FromStruct(document, sourceName) or, for an explicitly keyed body, Type.Create.FromStruct(rootKey, body, sourceName). Unkeyed callers omit the old null root-key argument. Replace applyToBuilder(builder, body, sourceName) with builder.applyStruct(body, sourceName); the method returns void. A generic helper needing its original typed Builder can return that same receiver after the call.

The exact erased Builder signatures applyStruct(Map) and applyStruct(Map, String) are now reserved. Rename colliding Schema methods or fields, including inherited and default-argument-generated collisions, then recompile. Old binary Builders overriding either signature cannot link against the final runtime methods. Other overloads remain permitted.

Both forms also offer ordinary overloads with generated diagnostic labels. Recompile and ship matched compiler/runtime and Schema artifacts. No released 4.1 reader compatibility is affected. Create.FromMap and managed Jackson remain unchanged. See structured Factory roots, active Builders, and Factory navigation.

Structured root Builder overlays

Ordinary root FromStruct signatures now accept a trailing closure, running Struct input then a cloned Builder overlay before one root PostApply. Existing no-overlay descriptors and ordered partial-failure semantics remain unchanged. Recompile Schema artifacts to expose the generated Factory members and refresh consumers/mirrors. Audit custom FromStruct overloads for collisions; their existing override authority remains. Untyped null in the source-name position may now be ambiguous with a Closure: cast to String for an explicit diagnostic label (null still rejects), or Closure<?> for no overlay. This applies to both document and explicit-key body forms. No Template/AsBuilder/Builder overlay variant is added. See root Builder overlays.

Structured input Template bodies

The additive Create.Template.FromStruct entry point accepts a parsed keyless root body and returns a reusable Template. Supply identity when constructing each recipient; see structured input Templates. Root creation and active Builder application now use the capabilities above.

Structured String operation selection

Use @Struct.Operation on one eligible Schema-authored String Builder method when several public operations share an external input name. Unmarked selection requires uniqueness; String and CharSequence overloads have no implicit specificity preference. Either exact signature can receive a String payload. Renamed/ignored overrides now replace inherited authored operation names and selection intent; inherited C1 converter override rejection remains unchanged.

Recompile participating Schema hierarchies with matching compiler/runtime/plugin artifacts for the new explicit operation completeness and selection facts (development protocol 1). Old or stripped facts reject before execution/generation. See String selection and ADR 0032.

String converter origins

Exact public String Builder projections now admit field closures, same-compilation non-DSL values and separately compiled external adapters. Missing or colliding generated projections still reject. Recompile matched compiler/runtime/plugin and Schema artifacts: every converter association now explicitly records whether C1 parameter facts apply. C1 assertions and policies remain unchanged on qualified routes; other origins emit String structure and field prose without inferring constraints. Exact String List-element and Map-value routes are covered by the later L1-A/L1-B extensions below; DSL-object conversion remains deferred. See converter authoring and schema output.

CharSequence scalar routes

An existing exact public CharSequence Builder projection now accepts a String scalar. Recompile matched Schema, compiler/runtime and plugin artifacts. All other payload kinds, including mutable CharSequence objects, still reject. Where a String closure and an implicit CharSequence factory now compete, exclude the unwanted factory with @Converters(excludeMethods = ['parse']) or expose one @Struct.Operation wrapper. No specificity preference selects one for you. C1 String parameter policies remain unchanged; CharSequence routes emit structural String grammar only. See the executable Duration example.

CharSequence container converter dispatch

Exact generated List-element and literal String-keyed Map-value CharSequence routes now accept raw Struct/YAML Strings. Ordinary generated Groovy calls also honor the recorded CharSequence signature: a runtime String no longer redispatches to a more-specific unprojected protected String factory. Ordinary GString calls retain the original argument through that same signature; Struct still rejects GStrings and arbitrary CharSequence values. Competing public converter routes retain their existing rejection. Recompile participating Schema hierarchies with matched compiler/runtime/plugin artifacts. See the example and compatibility boundary.

Concrete virtual structured scopes

The bounded @Field void method(ConcreteType value) family now accepts nested mapping input when the target is unkeyed/nongeneric, the annotation has no explicit options and one exact generated creator is proven. Recompile Schemas, including binary parents, with matched compiler/runtime/plugin artifacts. Unchanged inherited declarations remain usable; redeclared/overloaded sinks and other unsupported virtual shapes remain excluded. Do not replace an ordinary virtual closure with a no-argument creator followed by applyStruct: that changes callback and sink timing. See the executable scope example and schema representation. Ordinary Groovy, Factory, Template and Jackson APIs are unchanged; no closure delegate inference or CollectionFactory support is added.

String List-element converters

Exact List<T> fields with one compiler-proven generated String element adder now accept Lists of Strings through structured input. Recompile the Schema hierarchy with matched compiler/runtime/plugin artifacts; missing or corrupt converter association/completeness facts fail before execution. The unified metadata protocol remains version 1. Each element uses ordinary population, preserving defaults, order, indexed causes and earlier work on failure. JSON Schema emits structural String items without element-parameter constraint projection. Existing scalar C1 projection is unchanged. See the executable example.

Converter-backed Set elements

Exact Set<T> String element routes now accept ordered Struct/YAML sequences through the ordinary generated adder. Recompile matched Schema/compiler/runtime/plugin artifacts for the exact association. Each source element converts, including duplicates, before native Set insertion; defaults, equality/comparator behavior, Template recipes, lifecycle and earlier effects on indexed failure remain ordinary. Empty input makes zero calls. JSON Schema emits String arrays without uniqueness or result-order/cardinality promises. CharSequence-only routes and specialized Set declarations remain outside this slice. See Set elements.

String Map-value converters

Exact Map<String, T> fields with one compiler-proven generated String value adder now accept Maps of literal String keys to Strings. Recompile the hierarchy with matched compiler/runtime/plugin artifacts. The existing version-1 association/count metadata now also covers this exact shape; incomplete/corrupt facts fail before Schema initialization. Entry traversal follows the supplied Map, preserving ordinary defaults, replacement of an existing key and keyed partial failures. Non-String declared/input keys and custom key mapping are excluded from converter admission. JSON Schema emits String additionalProperties without value-parameter assertions or converter execution. This changes no whole-container or owned-DSL Map grammar. See Map values.

Native derived-key Map values

Native scalar/enum values in supported String-keyed Maps with @Field.keyMapping now accept Struct/YAML value sequences. Recompile the Schema hierarchy with matched compiler/runtime/plugin artifacts to replace its former population exclusion with the existing exact field/adder selection. Metadata remains version 1; public callable signatures are unchanged. Compatible descendant adder overrides follow ordinary Builder dispatch. Stored keys, replacement and failures use ordinary runtime mapping. Converter-backed and owned DSL values and non-String declared keys remain excluded. See derived-key Map values.

Compiled converter String input

Ordinary non-DSL fields with one eligible separately compiled String converter can now participate in structured input and JSON Schema. The selected parameter owns its Pattern facts and @Struct.ConstraintProjection policy; field policy and field domain-value constraints retain separate meaning. The finite Pattern recognizer is unchanged, and no runtime parameter enforcement is added. See converter authoring and projection rules.

Recompile participating Schema hierarchies with matched compiler/runtime/plugin and domain artifacts, including after converter contract changes. Required explicit converter association/completeness facts retain development protocol marker 1; old incomplete artifacts receive recompile guidance. Supply the domain, Jakarta API and referenced member types on the inspection classpath. There is no compatibility decoder or changed-JAR-without-recompilation guarantee.

Structured-input metadata protocol

Structured input and JSON Schema generation require Schemas compiled with a matching supported metadata protocol. Older or incomplete Builder contracts are rejected; recompile the participating Schema artifacts.

GeneratedInput.Schema.version=1 replaces the earlier feature-specific markers. Producers explicitly emit the supported version; the interpreter and generator require exactly it plus all required facts. This includes the declaring/inherited hierarchy and participating owned types in other projects or JARs. Missing, older, future or malformed versions and missing/corrupt required facts fail with Schema/Builder, artifact and recompile guidance before execution or schema replacement. Neither identity-only compatibility nor authored-operation reconstruction from old annotations remains. No version negotiation or mixed-version mode is supported. Authoring annotations and valid-Schema behavior are unchanged.

Composed constraints and documentary meta-annotations

First-level AND Bean composed constraints can now contribute the existing numeric and bounded Pattern assertions to JSON Schema. OR/ALL_FALSE, overrides, nested/repeatable or uncertain composition and unsupported mappings remain runtime descriptions. Independent assertions are preserved without reduction, including contradictory numeric bounds. Review generated schemas when adopting the change: supplied values can now be restricted by supported composing rules.

@Struct.ConstraintDescription is literal annotation-type prose. PROJECT/TEXT_ONLY retain it; OMIT suppresses it while keeping ordinary Javadoc, structural bounds, explicit examples and deprecation. Runtime enforcement and direct calls are unchanged. Recompile all participating declaring/inherited/owned Schema artifacts with matching compiler/runtime/plugin versions for complete composition/description facts. There is no Model/source fallback, and suppression cannot hide corrupt metadata. The development protocol marker remains 1; this is not a mixed-toolchain compatibility promise. See the supported boundary and example.

Advisory input examples

@Struct.Examples provides documentary strings. They are emitted as JSON Schema string examples, without parsing or validation against the property type or runtime constraints. Write @Struct.Examples(['localhost']), without JSON quoting. A note on a numeric, boolean or object property is still a string and is not promised to be a valid instance value.

Current development Builder facts retain source-specific string arrays, including empty absence arrays. The unified GeneratedInput.Schema.version remains 1; this slice adds no metadata version, feature gate or compatibility mechanism. Keep the current compiler/runtime/plugin aligned. See syntax and placement.

Conservative Pattern projection

Eligible direct singleton Jakarta Pattern constraints on ordinary String fields now project automatically under the existing PROJECT policy, using the bounded ASCII grammar and printable-ASCII guard described in JSON Schema. Unsupported forms remain runtime descriptions. Use TEXT_ONLY or OMIT for existing field-level control; input admission, defaults and completed runtime validation stay independent. No new task flag exists.

Recompile and package roots and participating inherited/owned Schemas with matching compiler/runtime/plugin versions. Explicit decoded regexp and flag-emptiness facts are required even for descriptive or omitted constraints. Missing or malformed metadata fails before execution or output replacement. GeneratedInput.Schema.version stays at its current value during 4.2 development; formal release-protocol cutover/recompilation preparation remains deferred. This grants no historical or mixed-toolchain compatibility promise.

Literal names and exclusion

Use @Struct.Name('literal') and marker @Struct.Ignore for dependency-free structured-input/JSON Schema shaping on eligible fields, selected construction keys and admitted Builder methods. Exact names add no alias. Compatible Jackson names coalesce; conflicting explicit names now fail with both origins, including excluded entries. Empty Struct.Name is invalid; empty Jackson names retain fallback. False Jackson ignore cannot undo Klum exclusion. Ordinary Groovy names and validation remain unchanged; Jackson import needs its own matching annotations when the same spelling is desired.

Recompile/package affected Schemas with matching compiler/runtime/plugin versions. Declaring public Builder contracts retain required effective name/exclusion/origin facts, including authored operations, under the shared metadata protocol. Missing/corrupt facts fail before execution or output replacement. An ignored key does not remove construction identity obligations. See structured input and JSON Schema.

Enum value names

Adding @Struct.Name to an enum constant replaces the constant's spelling in Structured Input. Update existing Struct/YAML documents that use its declared name and regenerate the associated JSON Schema. The token applies wherever the enum is admitted as a native input value. Ordinary Groovy continues to use its existing enum constants and converters. See enum value names.

Type naming profiles

@Struct.Naming now selects type-owned IDENTITY or bounded ASCII KEBAB_CASE for structured input and JSON Schema. Its profile is required. An explicit choice binds descendants, including explicit identity; an unannotated hierarchy leaves room for its first profiled child. Profiles cover inherited eligible members without changing standalone ancestors. Owned types resolve their own hierarchy. Existing Jackson literal overrides/exclusions stay supported alongside Klum literals. Managed Jackson import keeps its independent naming behavior.

Use matching compiler/runtime/plugin versions and recompile/package participating declaring and owned Schema artifacts. The shared metadata protocol requires explicit profile/absence facts for every participating hierarchy, including unprofiled/identity types. Older or incomplete contracts fail before execution or schema replacement; no Model-byte fallback fills gaps.

Inputs selecting kebab-case must use the new exact member names; native spelling is not an alias. Data/instance keys and literal overrides stay unchanged. Construction-key position rules remain in force. See structured input and generated schemas.

Advisory JSON Schema deprecation

Generated schemas now include deprecated: true for admitted Schema-deprecated members by default, independently of numeric constraints. Input admission and runtime behavior are unchanged. Missing advisory provenance omits this keyword when required numeric facts are complete; older incomplete numeric metadata requires recompilation. See deprecation.

Integral JSON Schema bounds

JSON Schema generation always projects supported direct integral and decimal bounds. Configure only roots:

klumSchema.jsonSchema { rootTypes.add('example.Capacity') }

The unreleased integralConstraints and decimalConstraints properties are removed without aliases or a replacement selector. Recompile/package root, inherited and owned dependency Schemas with matching compiler/runtime/plugin versions: complete supported numeric metadata is required for all generation. Missing facts fail before replacing previous output; Model bytes never fill gaps. Contradictory numeric declarations remain valid schema assertions, without satisfiability analysis. Construction, completed validation, omission, null admission and construction keys remain unchanged. See integral bounds and decimal bounds.

Opt-in structured Builder input

For caller-parsed Map/List/scalar data that should invoke admitted domain Builder operations, see Structured Input. Recompile and package Schema-generated metadata for this route. It adds no parser and leaves named-parameter/Jackson behavior unchanged. Use an already-prepared active Builder when early callbacks require Schema-specific dependencies; later LINK assignment does not supply earlier callbacks.

Structured zero-argument commands

Structured input now admits public Schema-authored zero-argument @Builder.Method commands with an empty mapping only (resetTimeout: {} in YAML). Blank YAML values and explicit null still reject. Existing Groovy/Java method behavior is unchanged; there are no implicit reset/clear semantics. See commands.

Recompile all participating Schema hierarchies with matching compiler/runtime/plugin artifacts. Each authored public operation now carries an explicit compiler role, checked against its exact signature; missing, malformed or inconsistent facts fail closed. The development metadata protocol remains version 1. This adds no mixed-toolchain compatibility.

Ordered structured-input failures

Structured input now checks and invokes operations in the supplied Map/List iteration order, recursively. A later invalid name, type or child no longer prevents earlier mutations or side effects. failed root construction returns no completed Model; Builder application may leave the caller's Builder partially configured. Neither route rolls back, resets or forces completion. Review callers that catch input exceptions and previously relied on an unchanged Builder. Decide explicitly whether to abandon their enclosing construction or continue with the partial state.

Structural entry and complete static contract checks remain before traversal. Required construction identity is read before allocating that root/child; a missing key stops that allocation even when other body members precede it. Earlier siblings can already have run. Typed operation arguments validate as one payload; population containers validate element by element. Generated JSON Schema still describes structural input, with no execution-order or successful-construction promise. See order and failures and ADR 0032, related to #952.

Explicit structured construction keys

#954 establishes actual key members for self-contained keyed documents. Use the actual key's external member name, including literal @JsonProperty renames. A caller-pre-keyed root retains its explicit identity; its body forbids an inner root key, even if equal. Active Builder targets likewise retain their existing identity.

A supplied direct caller-key child now requires its key before construction; input that previously reached construction with null identity rejects before that child's allocation. Omitted optional children remain legal. Fixed/derived/Cluster-key children and keyed Map values continue to forbid inner identity. Their providers and outer keys retain authority.

Generated keyed-root JSON Schema now describes the self-contained document and gains a required String key member. It no longer describes explicit-rootKey or active-Builder payloads. Admitted direct relationships with an ignored or colliding required key fail generation, including optional ones; retain and distinguish the previous successful output when generation fails. Use matching compiler/runtime/plugin versions and recompile binary parents as needed for key facts.

See construction-key examples and position-specific JSON Schema. Create.FromMap, ordinary Groovy DSL construction and managed Jackson keep their independent behavior. File/URL loading and broader grammar are separate work.

Literal CollectionFactory alternative input

Finite explicit compiler-literal alternatives on a default owned Map<String, abstract keyed DSL type> now accepts elements: {fixed: {primary: {value: configured}}, rolling: {secondary: {}}} when both aliases are declared. The one-alias form remains supported. Public creator/collection-scope convenience methods are not required by Struct; customizations retain their ordinary Groovy behavior. The outer String key owns construction identity; omit the inner key member even when equal. The existing concrete keyed-Map grammar is unchanged. Recompile matched Schema artifacts for the required association/count facts, including inherited artifacts. See the bounded family and its exclusions (#952, F2-B; #1030, multiple explicit groups).

Caller-pre-keyed Builder-body schemas

Default rootTypes schemas still require a keyed root's actual external key member. For an already keyed Builder body, select klumSchema.jsonSchema.bodyRootTypes explicitly. The same Model may appear in both sets, producing independent <Model>.schema.json and <Model>.builder-body.schema.json artifacts. The body artifact forbids root identity while retaining all child key positions. Public construction uses the accepted Factory/Builder boundary, with the interpreter internal; delivery of those remaining entry points is separate. No runtime call or filename-key convention changes. Choose the matching artifact explicitly; generation does not configure editors or file discovery. See the Gradle example (#953, S7).

To 4.1

Abstract Builder operations

Recompile Schemas to use general abstract @Builder.Method contracts on abstract DSL classes. Concrete subtype Builders must implement them; a subtype property may supply an inherited setter. These methods are absent from both completed Models and abstract Template Models. Parent-field Templates remain supported; executing an unrealized abstract Builder operation during Template definition requires defining the Template on an implementing concrete subtype. Abstract @Builder.Input/@Builder.Result methods remain rejected. See inheritance and Templates.

Explicit subtype creation with defaultImpl

Recompile Schemas whose abstract DSL relationship type declares defaultImpl and clients compiled against their Class-selected creator methods. Those methods now return the declared relationship's public Builder type, avoiding a cast to the default implementation's Builder when another compatible subtype is selected. This applies to direct owned/OPTIONAL_LINK, keyed, Collection, and Map creators. Implicit creators still return the default implementation's Builder; generated Create Factory selectors retain the exact selected Builder type. See default implementations.

Composing domain annotations

Annotation propagation adds default-only composition on DSL Schema classes, fields and methods. Upgrade the KlumAST compiler and annotation library together to a pairing that provides the marker and contributor; a new marker alone does not enable an older compiler. Use aligned KlumCast annotations/SPI/compiler 0.5.0 dependencies. Compile domain annotation libraries first, then recompile consuming Schemas after adding or changing requests.

When adopting a domain that now requests AutoCreate, remove the former bare explicit @AutoCreate from each use. Every duplicate involving propagation is rejected, including configured explicit uses, repeatable selections and nested domain-container uses. If a relationship needs customized key, type or value, retain a defaults-only domain with direct AutoCreate instead. Domain arguments are never forwarded to the selected annotation.

Keep propagating domains as ordinary annotations: selecting an AnnotationCollector is rejected, and collector rewriting of a propagating domain is unsupported. Existing compiled Schemas retain their emitted behavior until recompiled; there is no runtime interpreter or retrofit. Direct annotations remain valid. Editor alias recognition remains unqualified even when compilation and source mirrors work.

Propagation does not enable class-level defaults (#888), source composition (#548) or consumer provider-selection policy.

External lifecycle participants

The pre-4.1 development API is now owned by public final LifecycleParticipant (private constructor). This is a source and binary break without deprecated aliases. Update imports and recompile annotation libraries, handler libraries, Schemas and consumers together:

Former development type 4.1 type
LifecycleCreator (including List) LifecycleParticipant.Creator (including List)
LifecycleMutator (including List and SealedPolicy) LifecycleParticipant.Mutator (including List and SealedPolicy)
LifecycleCreationHandler<A> LifecycleParticipant.CreationHandler<A>
LifecycleMutationHandler<A> LifecycleParticipant.MutationHandler<A>
LifecycleFieldContext<A> LifecycleParticipant.InvocationContext<A>
LifecycleMutationContext<A> LifecycleParticipant.MutationContext<A>

MutationContext extends InvocationContext. Contexts remain valid for one invocation only; type mutation can have null fieldName and fieldType. Repeatable containers, FAIL/SKIP and lifecycle behavior are unchanged. See #883.

Domain annotations can select creators/mutators on direct DSL relationships in four existing Builder phases, or mutators on Schema types. Handlers use generated public Builder contracts; existing lifecycle callbacks remain valid. See Model Phases for context, sealed FAIL/SKIP, validation and module access. Collection/Map field annotations remain rejected, no HANDLE or Closure helper API is supplied, and late-created children never replay earlier phases. Existing ownership, session, Template/import and materialization rules still apply.

Discovering a Builder's Model type

The additive Model type getter KlumBuilderSupport.of(builder).getModelType() returns the represented concrete subtype without Schema recompilation. It uses the existing runtime export and remains readable before OWNER and after completion or abort. Ownership-query lifetime and mutation guards are unchanged.

Reading owning Schema declarations

The initial owning-declaration support is additive. Use KlumBuilderSupport.of(builder).getStructure() in the current active session after OWNER, and KlumObjectSupport.of(model).getStructure() for completed Objects. No Schema recompilation or generated-interface change is required solely for the facade. Existing LinkTo/LinkSource selection remains unchanged. Null completed Object receivers now throw NullPointerException("object"), matching the new Builder and annotation-query contract. The bounded Template/copy/import behavior and same-version serialization are qualified, as are Java 17 and dynamic/static Groovy 3/4/5 artifact consumers and Groovy 4/5 named modules. Existing qualified Schema package opens suffice; annotation lookup adds no field-value access requirement. Copied aliases retain their existing identity and behavior. Direct copied-container placements without authoritative claims return Optional.empty(), even when their location is unique; absence does not prove that an Object is a root. Normal OPTIONAL_LINK aggregation and recipe copying remain distinct existing routes; see their copy boundary. No copy-semantic repair or historical serialization promise is introduced.

Opting in to portable DelegatingScript IDE metadata

The IntelliJ DelegatingScript workflow is additive: existing factory calls, script bases, compiled script-class names, key derivation, and runtime receivers retain their behavior. The Schema owns and versions a literal suffix-to-Model mapping; Model projects explicitly opt in and select separate editor metadata. The preferred GMM selection follows the normal Schema version without repeating it; POM-only consumers repeat the exact GAV in the explicit gdsl classifier request. Refresh metadata and reload IntelliJ when mappings or Schema versions change.

If you experimented with the unreleased copied-resource recipe from PR #809, remove those copied contributors and adopt the Schema declaration. There is no migration scanner or automatic deletion of arbitrary external GDSL. The qualified contract covers regular non-nested Models; nested mirror/publication preparation is separately tracked in #826. Issue #805 remains open for release qualification.

To 4.0

4.0 replaces the generated mutable RW object with a true Builder and materializes a completed, structurally immutable DSL Object graph before validation. Completed models no longer expose generated apply, owned composition cannot adopt already completed objects, lifecycle extensions are split at the new INSTANTIATE phase, and collection declarations now have explicit snapshot-safe limits. Templates now have persistent graph-wide recipe identity separate from ordinary models; marked Templates cannot be relationship values or ordinary Jackson export values, and deferred Builder actions cannot be scheduled at phase 40 or later. Jackson is an asymmetric external-format integration rather than Klum persistence and adds no wire metadata.

See the dedicated Builder First Migration guide for the complete migration checklist and compatibility breaks, plus Templates, Copy Strategies, and Model Phases for materialization boundaries and Jackson Integration for foreign-data import and ordinary POJO export.

Opting in to owner-provided defaults

@OwnerProvidedDefaults is additive and opt-in. Existing unannotated Schemas need no migration and retain their generated factories, Builders, completed-model API, and lifecycle behavior. A Schema that adopts the annotation must compile and run with KlumAST annotation, compiler, and runtime artifacts that include the feature; recompile the Schema and its generated DSL support together after adding it. No generated method or type is added by the annotation.

The annotation provides owner-specific conservative defaults through a shared JavaBean contract. It is not a replacement for a generic mixin API or an overwrite-strategy migration. See Owner-provided defaults for its absence, ordering, identity, and warning rules.

Validation callers must import and catch com.blackbuild.klum.ast.runtime.validation.KlumValidationException. The former com.blackbuild.klum.ast.runtime.KlumValidationException type has been removed; this is an intentional 4.0 source and binary compatibility break.

Template creation and scoped application

Create a reusable Template below Create, then apply it below Template:

(See: TemplatesDocumentaryTest#'applies one scoped template to multiple service configurations'.)

def baseline = ServiceConfiguration.Create.Template.With(region: 'eu-central')

ServiceConfiguration.Template.With(baseline) {
    ServiceConfiguration.Create.With { }
}

Foo.Create.Template(...) and Foo.Create.TemplateFrom(...) have been removed so Foo.Create.Template can be the unambiguous generated Factory property. Migrate them to Foo.Create.Template.With(...) and Foo.Create.Template.From(...). The older documented Foo.Template.Create(...) and CreateFrom(...) spellings remain deprecated 4.x aliases; move new code to the canonical Create.Template chain. The best-effort Builder First migration helper recognizes only direct type-qualified occurrences. Run it in a clean, version-controlled schema-module worktree, inspect its diff, then compile and finish the checklist.

Code that explicitly named the generated scoped-application type must now use Foo_DSL.TemplateScope rather than Foo_DSL.Template. This intentional 4.0 RC source and binary compatibility break has no alias: recompile schemas and typed Java or static Groovy clients after changing the name. Foo_DSL.Factory.Template remains the distinct type for the literal Foo.Create.Template root-creation field.

For a foreign YAML/JSON migration, configure one caller-owned Jackson mapper, import one input into one Builder lifecycle, and treat the completed-model export as a separately owned external projection. Do not feed it back as Klum persistence or use repeated imports as a Jackson-specific merge/layering mechanism; #304 owns source-neutral composition.

Dynamic Template lookup in abstract hierarchies (4.1)

Recompile Schemas with the corrected 4.1 compiler to use ordinary Child.Template property syntax below an abstract DSL superclass. The hidden abstract Template implementation now has a distinct name so it cannot shadow the generated Template field in Groovy class-literal expressions. Generated public factory and scope interfaces keep their names. See Templates in a class hierarchy for the supported usage.

Regenerate previously Java-serialized abstract Templates from their source recipes after recompiling: serialization records the hidden implementation's binary name and is not a cross-version persistence format.

Generated inner-name collisions (4.1)

A nested Schema type cannot occupy the same binary name as a KlumAST implementation generated directly inside that DSL class. Compilation reports the conflicting type at its declaration and asks you to rename it, before Groovy reports a low-level duplicate-class error (#837). The exact names are:

  • Builder, _Factory, _Template, and _TemplateFactory for generated Builder, factory, and Template adapters;
  • _TemplateModel only when an abstract DSL class needs a generated Template implementation;
  • _<fieldName> only when a DSL collection field generates a collection factory;
  • _<clusterName> only when a Cluster selects fields and generates a Cluster factory;
  • _<fieldName>_converterClosures only when a field declares converter closures.

The rename diagnostic applies to source-declared nested types. Conflicts between generated implementations retain the compiler's duplicate-class rejection. For example, a collection factory and a nonempty Cluster both named services request the same implementation name; this is a generator conflict, not a nested type declaration to rename.

Only names actually generated for that class are reserved. Other underscore-prefixed nested types, such as _Recipe, remain valid. A concrete DSL class can still declare _TemplateModel, and a field without converter closures does not reserve its corresponding converter implementation name. These are compiler constraints; broader Schema style recommendations are tracked separately in #838.

Named modules and Groovy

Groovy 3 remains an ordinary-classpath configuration. Do not add a KlumAST module-info.java to a Groovy 3 schema or compensate with JVM module flags.

Groovy 4 and 5 schemas may be named modules and must require org.apache.groovy, the annotations/runtime modules, and requires static com.blackbuild.klum.ast.compiler; add adapter modules only when used. A schema that uses Jackson and Jakarta Bean Validation has this narrow descriptor shape:

module example.schema {
    requires com.blackbuild.klum.ast.annotations;
    requires com.blackbuild.klum.ast.runtime;
    requires static com.blackbuild.klum.ast.compiler;
    requires com.blackbuild.klum.ast.jackson;
    requires com.blackbuild.klum.ast.validation.bean;
    requires org.apache.groovy;

    exports example.schema;
    opens example.schema to com.blackbuild.klum.ast.runtime,
        com.fasterxml.jackson.databind,
        org.hibernate.validator;
}

Keep the runtime opening for generated Builder lifecycle/materialization. Add the Jackson and Hibernate Validator targets only when those adapters inspect the schema; do not substitute --add-reads, --add-exports, or --patch-module flags.

The Schema plugin validates this user-owned descriptor through validateKlumSchemaModule, which is part of check and Maven publication. It reports copyable missing requires and qualified opens directives but never rewrites module-info.java. The generated Foo_DSL mirrors used for IntelliJ completion are not module sources, compiler inputs, or publication inputs.

Recompile schemas and clients for 4.0. Java-serialized 3.x graphs are not 4.0 migration inputs, and Java serialization is not a cross-version persistence format; own external compatibility data and migrations in the Schema.

Custom validation reporting

Validator and ValidatorBase are removed in 4.0; there is no source or binary compatibility adapter. In lifecycle methods, lifecycle closures, and validation classes, replace their shortcuts with KlumSchemaSupport.getKlumValidation() (Groovy's klumValidation property) and its error, errorAt, issue, issueAt, suppressOn, or suppressAll operations. Use KlumSchemaSupport.klumValidationForObject(target) only when a lifecycle callback must report an issue on an explicit object. It retains that object's construction path and does not alter lifecycle ordering. The separate #406 compiler restriction remains a later placement check; it is not a migration fallback.

KlumCast 0.4 final dependencies

KlumAST 4.0 uses the immutable KlumCast 0.4.0 artifact set: klum-cast-annotations, klum-cast-spi, and klum-cast-compile. Its stable automatic module names are com.blackbuild.klum.cast.annotations, com.blackbuild.klum.cast.spi, and com.blackbuild.klum.cast.compiler; do not substitute filename-derived names or use local module-path flags to compensate for an invalid dependency graph.

To 2.0

The sections below describe historical migration steps and may show APIs, such as completed-model apply, that were subsequently removed in 4.0. Apply the historical migration first, then follow Builder First Migration.

Validation now throws KlumValidationException

which wraps KlumValidationResults for the validated objects, each containing the relevant KlumValidationIssues. Previously, an AssertionError was thrown, so calling code might need to be adjusted.

Multiple Inner Create Calls on the Same Field (or Key in a Map Field) Now Stack Instead of Replacing

Previously, multiple calls to the same inner create method would replace the previous value.

Foo.Create.With {
    bar {
        value = 1
        anotherValue = 2
    }
    bar {
        anotherValue = 3
    }
}

Previously, the second call of "bar" would result in a new object, i.e. the object created by the first call would be replaced, resulting in:

foo.bar.anotherValue == 3
foo.bar.value == null

Now those calls stack, so the result would be:

foo.bar.anotherValue == 3
foo.bar.value == 1

This is especially useful for using deep templates to set the first object:

def template = Foo.Create.Template {
    bar {
        value = 1
        anotherValue = 2
    }
}

Foo.withTemplate(template) {
  Foo.Create.With {
      bar {
          anotherValue = 3
      }
  }
}

If the existing object does not match the new object (either because a different key is provided or specific type is given that is different from the existing type), an Exception is thrown. In that case, the behaviour can be explicitly overridden by using either apply or a setter (to explicitly merge or replace):

Foo.withTemplate(template) {
  Foo.Create.With {
      bar.apply { // explicitly force merge
          anotherValue = 3
      }
  }
}

or

Foo.withTemplate(template) {
  Foo.Create.With {
      bar = Bar.Create.With { // explicitly force overwrite
          anotherValue = 3
      }
  }
}

Default Values are actually set, not only returned

This makes objects used in copyFrom behave differently. Previously, the copyFrom methode explicitly ignored default values, now they would be copied as well if already set. This can lead to different results if the copy source a) is not a template object and b) was created outside the current phase run.

If the object was created outside the phase run, it will most likely be a template, so using the Create.Template() creator method (or the deprecated createAsTemplate() method) will lead to the same result as before.

Owners are now set in the owner phase

Previously, they have been set before apply was called, so apply had already access to the owner, which could be used in separate scripts. Any logic accessing the owner must be placed in a later phase (for example AutoLink or PostTree).

This also holds true for methods using default values populated by the owner.

PostApply methods accessing the owner must also be move to a later phase (or split).

Layer 3 @LinkTo relationships

In 4.0, @LinkTo is an OPTIONAL_LINK relationship by default. A local Builder created in the current construction session remains owned composition; an already owned Builder or a completed DSL Object is an aggregation target. This preserves the usual Layer 3 pattern in which a local value overrides an Auto-Link fallback.

Use @Field(FieldType.LINK) @LinkTo when the field must be aggregation-only. Ordinary relationships remain composition-only and reject completed or already claimed Builders. Custom @AutoLink code that previously overwrote a configured value must use builder.link(fieldName, target) for an explicit non-destructive fallback instead.

Deprecation: Validation annotation -> Validate

@Validation.mode() is replaced by phases and thus ignored. Validation.Option.IGNORE_UNMARKED is default anyway, so the only useful variation of the annotation is @Validation(option=VALIDATE_UNMARKED), which is replaced by @Validate on class level.

Deprecation: Factory methods -> Factory class

All static factory methods on DSL classes are deprecated in favor of a single Create class field which encapsulates all relevant factory methods.

The following factory calls should be renamed:

Old New
Foo.create() Foo.Create.One()
Foo.create(...) Foo.Create.With(...)
Foo.createFrom(...) Foo.Create.From()
Foo.createAsTemplate(...) Foo.Create.Template(...)
Foo.createFromClasspath(...) Foo.Create.FromClasspath(...)

Dependency changes

For 2.0, the single klum-ast dependency is replaced by two KlumAST is split into three distinct jars:

klum-ast-annotations

Does not usually need to be addressed directly except in very special cases, since it is a dependency of both of the other jars.

klum-ast

Contains the actual AST transformations, i.e. the core of KlumAST. These need to be present during compile-time only and need not be present on runtime (usually it should be safe if they are).

Contains classes needed during runtime.

Since klum-ast now relies on a runtime component, a schema now should have two separate dependencies, klum-ast as compileOnly (provided for Maven) and and klum-ast-runtime as api (runtime for Maven), i.e.:

  implementation 'com.blackbuild.klum.ast:klum-ast-runtime:4.2.0-rc.2'
}

or

<dependencies>
  <dependency>
    <groupId>com.blackbuild.klum.ast</groupId>
    <artifactId>klum-ast</artifactId>
    <version>...</version>
    <optional>true</optional>
  </dependency>
  <dependency>
    <groupId>com.blackbuild.klum.ast</groupId>
    <artifactId>klum-ast-runtime</artifactId>
    <version>...</version>
    <scope>runtime</scope>
  </dependency>
</dependencies>

To 1.2

DelegateOnly Strategy for closures

Closures are all DelegateOnly instead of the previous DelegateFirst. This means that you cannot access methods of an outer object directly (which would not be very intuitive). If you need this functionality, you need to access the outer object directly, using the owner property of Closure, an @Owner field of the outer instance or a local variable pointing to the targeted instance.

Instead of:

Foo.create {
    bar {
        methodInFoo()
    }
}

Write instead:

Foo.create {
    bar {
        owner.methodInFoo() // owner is property of Closure
    }
}

Note that naming an @Owner field actually owner leads to the field being overshadowed by the owner field of the closure. While this is usually not a problem, it might cause failures when used inside a Collection-Factory:

@DSL
class Bar {
  @Owner
  Foo owner
}

Foo.create {
    bars {
        bar {
            // owner points to the owner of the closure, i.e. the collection factory, so this will fail:
            owner.doSomething()
        }
    }
}

Calling the owner field (or any other field) actually owner leads to a compiler warning (which might eventually be replace with a compiler error). Consider using a more domain specific field name like graph or parent is advisable.
